확장 ACL은 출발지 주소뿐 아니라 목적지 주소, 프로토콜, 포트 번호까지 조건으로 쓴다. 어떤 호스트가 어떤 서버의 어떤 서비스에 접근하는지까지 구분해서 허용하거나 막을 수 있다.

## 한 줄의 구성

![확장 ACL 한 줄이 동작, 프로토콜, 출발지 주소, 출발지 포트, 목적지 주소, 목적지 포트 순서로 이루어지는 구성과 포트 연산자]({{ '/assets/img/ccna/day36-syntax.svg' | relative_url }})

- 프로토콜은 `ip`, `tcp`, `udp`, `icmp` 등을 쓴다. `ip`는 모든 IP 패킷을 뜻한다
- 주소는 표준 ACL과 같이 와일드카드 마스크로 쓰고, `host`와 `any`도 쓸 수 있다
- 포트는 `tcp`와 `udp`일 때만 지정할 수 있다. `eq`, `neq`, `gt`, `lt`, `range` 연산자를 쓴다
- 포트 이름 대신 번호를 써도 된다. `eq 80`과 `eq www`는 같다
- 번호 ACL의 범위는 100~199, 2000~2699이다

## 표준 ACL과의 차이

![표준 ACL과 확장 ACL을 번호 범위, 확인 항목, 적용 위치, 명령으로 비교한 표]({{ '/assets/img/ccna/day36-compare.svg' | relative_url }})

## 설정

PC1 대역은 서버 10.0.0.10의 웹(TCP 80)만 허용하고, 다른 서버 접근은 모두 막는 예이다.

```
R1(config)# ip access-list extended WEB-ONLY
R1(config-ext-nacl)# 10 permit tcp 192.168.1.0 0.0.0.255 host 10.0.0.10 eq 80
R1(config-ext-nacl)# 20 permit icmp 192.168.1.0 0.0.0.255 host 10.0.0.10
R1(config-ext-nacl)# 30 deny ip any host 10.0.0.10
R1(config-ext-nacl)# 40 permit ip any any
```

- 10번: 서버로 가는 웹 통신을 허용한다
- 20번: ping(ICMP)도 허용한다
- 30번: 그 외에 서버로 가는 통신을 모두 거부한다
- 40번: 나머지 목적지로 가는 통신은 허용한다. 이 줄이 없으면 암묵적 `deny any`에 걸려 다른 통신이 모두 막힌다

번호 ACL로 쓰면 다음과 같다.

```
R1(config)# access-list 100 permit tcp 192.168.1.0 0.0.0.255 host 10.0.0.10 eq 80
R1(config)# access-list 100 deny ip any host 10.0.0.10
R1(config)# access-list 100 permit ip any any
```

줄 끝에 `log`를 붙이면 일치한 패킷이 로그로 남는다. 어떤 통신이 걸리는지 확인할 때 쓰지만, 트래픽이 많은 줄에 붙이면 장비에 부담이 된다.

## 적용 위치

![PC2가 서버로 가는 통신만 막는 구성에서 출발지에 가까운 R1 Gi0/0 inbound에 확장 ACL을 적용한 그림]({{ '/assets/img/ccna/day36-placement.svg' | relative_url }})

확장 ACL은 막을 통신을 정확히 고를 수 있으므로 출발지에 가깝게 적용한다. 막을 패킷이 일찍 버려져서 필요 없는 트래픽이 네트워크를 지나가지 않는다. 다른 목적지로 가는 통신은 조건에 일치하지 않아 영향을 받지 않는다.

```
R1(config)# interface gigabitethernet 0/0
R1(config-if)# ip access-group WEB-ONLY in
```

- 출발지에 가까운 인터페이스의 `in`이 가장 흔한 조합이다
- 한 인터페이스에는 방향마다, 프로토콜(IPv4)마다 ACL 하나만 적용할 수 있다
- ACL은 상태를 기억하지 않는다. 한쪽 방향만 허용하면 돌아오는 패킷이 다른 인터페이스의 ACL에 걸려 통신이 실패할 수 있다

## 돌아오는 통신

TCP 통신은 응답 패킷의 출발지와 목적지가 요청과 반대가 된다. 서버 쪽에서 나가는 응답을 막는 ACL이 있으면 요청이 도착해도 연결이 만들어지지 않는다.

- 응답 방향에 ACL을 걸 때는 출발지 포트가 80인 패킷을 허용하는 식으로 쓴다. 예: `permit tcp host 10.0.0.10 eq 80 192.168.1.0 0.0.0.255`
- `established` 키워드를 붙이면 ACK 또는 RST 플래그가 켜진 TCP 패킷, 즉 이미 시작된 연결의 패킷만 일치한다. 바깥에서 먼저 시작하는 연결을 막고 안쪽에서 시작한 연결의 응답만 받을 때 쓴다

```
R1(config)# access-list 101 permit tcp any 192.168.1.0 0.0.0.255 established
```

## 확인

```
R1# show access-lists
Extended IP access list WEB-ONLY
    10 permit tcp 192.168.1.0 0.0.0.255 host 10.0.0.10 eq www (25 matches)
    20 permit icmp 192.168.1.0 0.0.0.255 host 10.0.0.10 (4 matches)
    30 deny ip any host 10.0.0.10 (9 matches)
    40 permit ip any any (120 matches)
```

`show access-lists`의 matches로 어느 줄이 쓰이는지 본다. 적용 상태는 `show ip interface gigabitethernet 0/0`에서 `Inbound access list is WEB-ONLY`로 확인한다. 안 되는 통신이 있으면 줄 순서, 방향(in/out), 돌아오는 패킷이 막히는지를 순서대로 본다.

## 주의할 점

- 범위가 좁은 조건을 위에 둔다. `permit ip any any`를 위에 두면 아래 줄은 평가되지 않는다
- ACL을 한 줄씩 추가하면 맨 아래에 붙으므로, 번호 ACL에서는 `deny` 줄 뒤에 추가한 `permit`이 효과가 없을 수 있다. 이름 ACL에서 시퀀스 번호를 지정해 끼워 넣는다
- `permit ip any any`를 빼먹으면 나머지 통신이 모두 막힌다
- 적용 방향을 반대로 걸면 조건의 출발지와 목적지가 맞지 않아 일치하지 않는다

## 확인 문제

1. 확장 ACL이 표준 ACL과 달리 조건으로 쓸 수 있는 항목을 세 가지 쓰시오.
2. 192.168.1.0/24에서 서버 10.0.0.10의 TCP 443으로 가는 통신을 허용하는 확장 ACL 줄을 번호 ACL 100으로 쓰시오.
3. 확장 ACL은 출발지와 목적지 중 어디에 가깝게 적용하는 것이 원칙인가? 이유도 쓰시오.
4. 확장 ACL의 번호 범위를 두 가지 쓰시오.
5. `established` 키워드가 있는 줄은 어떤 TCP 패킷에 일치하는가?
