호스트마다 IP 주소, 마스크, 게이트웨이, DNS를 손으로 넣으면 장비가 늘수록 실수도 늘어난다. 오늘은 이 값을 자동으로 나눠 주는 DHCP(Dynamic Host Configuration Protocol)를 다룬다.

## DHCP가 주는 것

DHCP 서버는 클라이언트에 일정 기간 동안 주소를 빌려 준다. 이 기간을 임대(lease)라고 한다. 주소만 주는 것이 아니라 다음 값을 한꺼번에 내려 준다.

- IP 주소와 서브넷 마스크
- 기본 게이트웨이
- DNS 서버 주소
- 임대 기간

DHCP는 UDP를 쓰며 서버는 67번, 클라이언트는 68번 포트를 쓴다. 서버는 전용 서버 장비일 수도 있고, 라우터나 L3 스위치가 겸할 수도 있다.

## DORA 4단계

![클라이언트와 DHCP 서버가 Discover, Offer, Request, Ack 순서로 메시지를 주고받는 순서도]({{ '/assets/img/ccna/day29-dora.svg' | relative_url }})

주소를 받는 과정은 메시지 네 개의 머리글자를 따 DORA라고 부른다.

| 단계 | 방향 | 전송 방식 | 내용 |
|------|------|-----------|------|
| Discover | 클라이언트 → 서버 | 브로드캐스트 | 서버를 찾는다 |
| Offer | 서버 → 클라이언트 | 브로드캐스트 또는 유니캐스트 | 빌려 줄 주소와 설정을 제안한다 |
| Request | 클라이언트 → 서버 | 브로드캐스트 | 제안을 수락한다 |
| Ack | 서버 → 클라이언트 | 브로드캐스트 또는 유니캐스트 | 임대를 확정한다 |

Discover를 보낼 때 클라이언트는 아직 주소가 없으므로 출발지가 0.0.0.0이고 목적지가 255.255.255.255이다. 같은 네트워크에 서버가 둘 이상이면 Offer도 둘 이상 올 수 있다. Request를 브로드캐스트로 보내는 이유는 어느 서버의 제안을 고르는지 모든 서버가 알게 해서, 선택받지 못한 서버가 제안했던 주소를 풀에 되돌리게 하기 위해서이다.

## 임대 갱신

![임대 기간 중 50퍼센트 지점의 T1과 87.5퍼센트 지점의 T2에서 갱신을 시도하는 시간축]({{ '/assets/img/ccna/day29-lease.svg' | relative_url }})

임대 기간이 절반(T1)이 지나면 클라이언트는 주소를 준 서버에 유니캐스트로 Request를 보내 갱신을 요청한다. 서버가 Ack를 주면 기간이 다시 처음부터 시작된다. 갱신이 안 되면 87.5%(T2) 시점에 브로드캐스트로 다른 서버에도 요청한다. 끝까지 갱신하지 못하면 임대가 만료되어 주소를 쓸 수 없고, 처음부터 DORA를 다시 한다.

Cisco IOS 서버의 기본 임대 기간은 하루이다. 사무실처럼 장비가 거의 바뀌지 않는 곳은 길게, 카페나 행사장처럼 사람이 계속 바뀌는 곳은 짧게 잡는다. 임대 기간이 길수록 주소 풀이 빨리 고갈되지 않지만 오래 안 쓰는 주소가 묶여 있게 되고, 짧을수록 풀은 잘 돌아가지만 갱신 트래픽이 늘어난다.

## 라우터를 DHCP 서버로 설정

게이트웨이로 쓰는 주소는 풀에서 빼야 한다. 먼저 제외할 주소를 지정하고, 풀을 만든다.

```
R1(config)# ip dhcp excluded-address 192.168.10.1 192.168.10.20
R1(config)# ip dhcp pool LAN10
R1(dhcp-config)# network 192.168.10.0 255.255.255.0
R1(dhcp-config)# default-router 192.168.10.1
R1(dhcp-config)# dns-server 8.8.8.8
R1(dhcp-config)# domain-name example.com
R1(dhcp-config)# lease 7
```

`lease 7`은 7일이다. 일, 시간, 분 순으로 쓸 수 있다. `ip dhcp excluded-address`는 풀에서 제외할 주소 범위를 지정하며, 게이트웨이나 서버처럼 고정 주소를 쓰는 장비의 주소를 여기에 넣는다. 이 명령을 빼면 서버가 이미 쓰는 주소를 클라이언트에 빌려 줘 주소 충돌이 생긴다. 라우터 인터페이스를 클라이언트로 만들려면 `ip address dhcp`를 쓴다.

## DHCP Relay

![PC와 DHCP 서버가 서로 다른 서브넷에 있을 때 라우터가 브로드캐스트를 유니캐스트로 바꿔 서버에 전달하는 구성도]({{ '/assets/img/ccna/day29-relay.svg' | relative_url }})

Discover는 브로드캐스트라 라우터를 넘지 못한다. DHCP 서버를 한 곳에 두고 여러 VLAN과 서브넷이 함께 쓰려면 라우터가 대신 전달해 줘야 한다. 이 기능이 DHCP Relay이다. 클라이언트가 있는 쪽 인터페이스에 서버 주소를 지정한다.

```
R1(config)# interface GigabitEthernet0/0
R1(config-if)# ip helper-address 10.0.0.5
```

라우터는 받은 브로드캐스트를 서버 주소로 향하는 유니캐스트로 바꿔 보내고, 메시지의 giaddr(Gateway IP Address) 칸에 그 인터페이스의 주소를 적는다. 서버는 giaddr를 보고 어느 서브넷의 클라이언트인지 알아 맞는 풀에서 주소를 고른다. 그래서 서버에는 서브넷마다 풀이 따로 있어야 한다. `ip helper-address`는 DHCP 말고도 TFTP, DNS 같은 몇 가지 UDP 브로드캐스트도 함께 전달한다.

## 확인 명령

```
R1# show ip dhcp binding
R1# show ip dhcp pool
R1# show ip dhcp conflict
```

`show ip dhcp binding`은 어느 MAC 주소에 어느 IP를 빌려 줬고 언제 만료되는지를 보여 준다. `show ip dhcp pool`은 풀의 범위와 사용 중인 주소 수를 보여 주고, `show ip dhcp conflict`는 충돌이 감지된 주소를 보여 준다. 클라이언트가 주소를 못 받으면 서버 풀이 비었는지, 같은 서브넷에 서버가 있는지, Relay라면 `ip helper-address`가 클라이언트 쪽 인터페이스에 있는지 순서대로 본다. 윈도우 PC는 DHCP 서버를 못 찾으면 169.254.0.0/16 대역의 주소를 스스로 붙이므로, PC에서 이 대역의 주소가 보이면 DHCP 실패를 의심한다.
