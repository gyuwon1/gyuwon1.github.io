네트워크가 돌아가려면 이름 풀이, 시각 맞추기, 상태 감시, 로그 수집이 뒤에서 받쳐 줘야 한다. 오늘은 이 네 가지 서비스를 한 번에 정리한다.

## DNS

DNS(Domain Name System)는 www.example.com 같은 이름을 IP 주소로 바꿔 준다. 이름과 번호를 짝지어 둔 전화번호부에 가깝다. 질의는 보통 UDP 53번 포트를 쓰고, 응답이 커서 UDP에 담기지 않으면 TCP 53번을 쓴다.

![PC가 리졸버에 질의하면 리졸버가 루트 서버, com 서버, example.com 권한 서버에 차례로 물어 주소를 얻는 구성도]({{ '/assets/img/ccna/day30-dns.svg' | relative_url }})

PC는 설정된 DNS 서버(리졸버)에 한 번만 묻는다. 리졸버는 모르는 이름이면 루트 서버, TLD(com) 서버, 해당 도메인의 권한 서버 순으로 찾아가 답을 얻고, 그 답을 TTL 동안 캐시에 저장한다. 같은 이름을 다시 물으면 캐시에서 바로 답한다.

주요 레코드 종류는 다음과 같다.

| 레코드 | 내용 |
|--------|------|
| A | 이름에 대응하는 IPv4 주소 |
| AAAA | 이름에 대응하는 IPv6 주소 |
| CNAME | 다른 이름의 별칭 |
| MX | 메일 서버 |
| NS | 해당 도메인을 담당하는 DNS 서버 |
| PTR | 주소에서 이름을 찾는 역방향 조회 |

Cisco 라우터를 DNS 클라이언트로 쓰려면 서버 주소를 넣는다.

```
R1(config)# ip name-server 8.8.8.8
R1(config)# ip domain name example.com
R1(config)# ip domain lookup
R1# ping www.example.com
```

`ip domain lookup`은 기본으로 켜져 있다. 명령어를 잘못 치면 라우터가 그것을 호스트 이름으로 보고 DNS 조회를 하느라 멈춘 것처럼 보일 수 있는데, 이때 `no ip domain lookup`으로 끈다.

## NTP

NTP(Network Time Protocol)는 장비들의 시계를 맞춘다. UDP 123번을 쓴다. 시각이 어긋나면 로그를 장비끼리 비교할 수 없고, 인증서 유효 기간 확인도 틀어진다.

![stratum 0에서 3까지 시각이 내려가는 계층 구조와 라우터가 NTP 서버에 시각을 요청하는 흐름]({{ '/assets/img/ccna/day30-ntp.svg' | relative_url }})

NTP는 stratum이라는 계층 번호로 기준에서의 거리를 나타낸다. stratum 0은 원자시계나 GPS 같은 기준 장치이고, 거기에 직접 연결된 서버가 stratum 1이다. 서버에서 시각을 받는 장비는 서버의 stratum에 1을 더한 값을 갖는다. 번호가 작을수록 기준에 가깝고, 16은 동기화되지 않은 상태를 뜻한다.

```
R1(config)# ntp server 10.0.0.1
R1# show ntp status
R1# show ntp associations
R1# show clock
```

`show ntp status`는 동기화 여부와 stratum을 보여 주고, `show ntp associations`는 어느 서버와 연결되어 있는지 보여 준다. 외부 서버가 없는 실습 환경에서는 라우터를 `ntp master 3`처럼 설정해 스스로 서버가 되게 할 수 있다. 뒤의 숫자가 그 장비의 stratum이다.

## SNMP

SNMP(Simple Network Management Protocol)는 관리 서버(NMS)가 장비의 상태를 읽거나 설정을 바꾸는 프로토콜이다. 장비에서 돌아가는 SNMP 에이전트가 정보를 가지고 있고, 그 정보는 MIB라는 트리에 OID 번호로 정리되어 있다. 인터페이스 상태, CPU 사용률, 트래픽 양 같은 값이 여기에 들어 있다.

| 동작 | 방향 | 내용 |
|------|------|------|
| get | NMS → 장비 | 값을 읽는다 |
| set | NMS → 장비 | 값을 바꾼다 |
| trap | 장비 → NMS | 이벤트를 알린다. 응답은 없다 |
| inform | 장비 → NMS | trap과 같지만 NMS가 확인 응답을 준다 |

get과 set 요청은 장비의 UDP 161번으로, trap과 inform은 NMS의 UDP 162번으로 간다.

버전은 세 가지다. v1과 v2c는 커뮤니티 문자열을 비밀번호처럼 쓰며 평문으로 전송되므로 보안이 약하다. v3는 사용자 인증과 암호화를 지원하며 세 단계가 있다.

| 보안 수준 | 인증 | 암호화 |
|-----------|------|--------|
| noAuthNoPriv | 사용자 이름만 | 없음 |
| authNoPriv | 있음 | 없음 |
| authPriv | 있음 | 있음 |

```
R1(config)# snmp-server community READONLY ro
R1(config)# snmp-server host 10.0.0.9 version 2c READONLY
R1(config)# snmp-server enable traps
```

`ro`는 읽기 전용, `rw`는 읽기와 쓰기이다. 실무에서는 `rw` 커뮤니티를 거의 쓰지 않고, 쓰더라도 접근 가능한 주소를 ACL로 제한한다.

## Syslog

Syslog는 장비가 이벤트 메시지를 서버로 보내 모아 두는 방식이다. UDP 514번을 쓴다. 메시지에는 심각도가 붙는다.

![Syslog 심각도 0부터 7까지의 표와 장비에서 Syslog 서버 및 SNMP 관리 서버로 가는 경로]({{ '/assets/img/ccna/day30-syslog.svg' | relative_url }})

| 숫자 | 이름 |
|------|------|
| 0 | Emergency |
| 1 | Alert |
| 2 | Critical |
| 3 | Error |
| 4 | Warning |
| 5 | Notice |
| 6 | Informational |
| 7 | Debugging |

숫자가 작을수록 심각하다. 레벨을 정하면 그 레벨과 그보다 심각한 메시지가 모두 나온다. 예를 들어 레벨 4(warnings)로 정하면 0부터 4까지가 출력된다.

```
R1(config)# service timestamps log datetime msec
R1(config)# logging host 10.0.0.9
R1(config)# logging trap warnings
R1(config)# logging buffered 16384
R1# show logging
```

메시지는 `%LINK-3-UPDOWN: Interface GigabitEthernet0/1, changed state to down`처럼 생겼다. %다음에 기능 이름, 심각도 숫자, 니모닉 순으로 나오고 뒤에 설명이 붙는다. 위 예에서 3이 심각도(Error)이다. `logging trap`은 서버로 보낼 레벨이고, `logging buffered`는 장비 메모리에 쌓아 둘 때 쓴다. 시각 정보가 로그에 정확히 들어가려면 NTP가 맞아야 하므로 두 서비스는 함께 설정한다.

## 확인 문제

1. DNS 질의에 기본으로 쓰는 포트 번호와 프로토콜은 무엇인가?
2. DNS의 CNAME 레코드와 PTR 레코드는 각각 무엇을 나타내는가?
3. NTP에서 stratum 1 서버에서 시각을 받는 라우터의 stratum은 얼마인가?
4. SNMP에서 장비가 NMS에 이벤트를 알릴 때 쓰는 동작과 목적지 포트는 무엇인가?
5. `logging trap warnings`로 설정하면 심각도 몇 번까지의 메시지가 서버로 전송되는가?

<details>
<summary>정답 보기</summary>

1. UDP 53번이다. 응답이 크면 TCP 53번을 쓴다.
2. CNAME은 다른 이름의 별칭이고, PTR은 IP 주소에서 이름을 찾는 역방향 조회이다.
3. stratum 2이다.
4. trap(또는 inform)이고, NMS의 UDP 162번으로 보낸다.
5. 0번부터 4번까지이다.
